## 🔴 1. التحقق من Row Level Security على Supabase

**البند الأهم في هذا المستند.**

التطبيق ملفات ثابتة تتحدث إلى Supabase مباشرة، ومفتاح `anon` علني بحكم التصميم
(موجود في الكود، وفي حزمة الجافاسكربت المنشورة، ويمكن لأي زائر قراءته من أدوات
المطوّر). كل فحوص الصلاحيات في `App.jsx` — دور `admin`، ملكية الجلسة، إجبار
تغيير كلمة المرور — **تعمل في المتصفح فقط، وكلها قابلة للتجاوز**.

يعني ذلك أنه ما لم تكن RLS مفعّلة ومضبوطة، يستطيع أي شخص على الإنترنت:

- نشر جلسة دون مراجعة: `PATCH /rest/v1/videos?id=eq.<id>` بـ `{"published":true}`
- حذف جلسات الآخرين: `DELETE /rest/v1/videos?id=eq.<id>`
- قراءة كل الملفات الشخصية: `GET /rest/v1/profiles?select=*`
- تعطيل إجبار تغيير كلمة المرور بتعديل `must_change_password`

**المطلوب التحقق منه في لوحة Supabase** (لم أتحقق — يحتاج وصولاً إلى المشروع):

1. `ALTER TABLE videos ENABLE ROW LEVEL SECURITY;` و`profiles` كذلك.
2. سياسة قراءة عامة على `videos` مقيّدة بـ `published = true` فقط.
3. سياسة `INSERT` تشترط `auth.uid() = owner_id`، ومع فرض `published = false`.
4. سياسة `UPDATE`/`DELETE` تشترط ملكية الصف، مع **حصر تعديل `published`
   بدور `admin`** — وإلا استطاع الناشر نشر نفسه ذاتياً وتعطّلت المراجعة كلها.
5. سياسة `UPDATE` على `profiles` تمنع المستخدم من تعديل `role` الخاص به.

اختبار سريع من الطرفية (يجب أن يفشل جميعها للزائر المجهول):

```bash
curl -X PATCH "$SUPABASE_URL/rest/v1/videos?id=eq.<id>" \
  -H "apikey: $ANON" -H "Content-Type: application/json" \
  -d '{"published":true}'
```

## 🔴 2. ملف `seed-members.mjs` غير موجود

التعليق في رأس `App.jsx` ينصّ على أن الحسابات «تُنشأ من العمادة عبر
`seed-members.mjs` فقط»، لكن **الملف غير موجود في المستودع**.

الأثر: لا توجد طريقة موثّقة أو قابلة لإعادة الإنتاج لإنشاء الأعضاء، والعملية
تعتمد على ملف محلي عند شخص واحد.

المقترح: إضافة السكربت (مع استخدام `service_role` من متغيّر بيئة **لا** من
الكود) وتوثيق تشغيله، أو تصحيح التعليق ليصف الواقع.

## 🟠 3. ثغرة منطقية في مسار المراجعة

في `Admin.act()` رفض الجلسة = **حذفها نهائياً**:

```js
if (publish) await api.setPublished(id, true, token);
else await api.remove(id, token);   // حذف لا رجعة فيه
```

لا تأكيد قبل الحذف، ولا سبب رفض يصل الناشر، ولا إمكانية تعديل وإعادة إرسال.

المقترح: إضافة حالة `rejected` مع حقل `rejection_reason` بدل الحذف، وتأكيد قبل
أي حذف فعلي.

---

## 🟠 4. الجلسة لا تُحفظ

حالة الدخول في `useState` فقط، دون `localStorage` أو `sessionStorage`. أي تحديث
للصفحة يُخرج المستخدم ويفقد سياقه.

المقترح: استخدام مكتبة `@supabase/supabase-js` الرسمية التي تتكفّل بحفظ الجلسة
وتجديد الرمز تلقائياً، بدل طبقة `fetch` اليدوية الحالية.

## 🟠 5. لا يوجد router

التنقل بمتغيّر `view` داخل الحالة. النتيجة:

- لا يمكن مشاركة رابط مباشر لجلسة — وهذا جوهري لمنصة محتوى.
- زر الرجوع في المتصفح يغادر الموقع.
- لا أرشفة للصفحات في محركات البحث.

المقترح: `react-router` مع `basename="/NajahBCVideoPlatform"`، ومسار
`/video/:id`. يحتاج GitHub Pages ملف `404.html` لإعادة التوجيه.

## 🟠 6. فحص آلي على الـ Pull Request

يوجد حالياً إجراء **نشر** فقط، ولا يوجد إجراء **فحص**. أي PR يمكن دمجه دون أن
يبني أحد الكود، وأول اكتشاف للعطل يكون على الموقع المباشر.

الملف جاهز في [`ci-workflow.example.yml`](ci-workflow.example.yml). لتفعيله:

```bash
cp docs/ci-workflow.example.yml .github/workflows/ci.yml
gh auth refresh -s workflow    # مطلوب لدفع ملفات workflows
git add .github/workflows/ci.yml && git commit -m "chore: فحص آلي على الـ PR"
```

> لم يُوضع في `.github/workflows/` مباشرة لأن دفع ملفات سير العمل يتطلب صلاحية
> `workflow` غير المتوفرة في الرمز المستخدم حالياً.

## 🟡 7. بيانات مكرّرة في جدول `videos`

`AddVideo` يكتب `owner_name` و`department` و`division` في صف الفيديو، بينما
`listPublished()` تقرأها من `profiles` عبر join وتتجاهل المنسوخة:

```js
// يُكتب عند الإضافة
{ owner_id, owner_name, department, division, ... }

// يُقرأ عند العرض — من profiles لا من videos
"videos?select=*,profiles(username,department,division)&published=eq.true"
```

مصدران للحقيقة، وأحدهما ميّت. الأثر: تعديل قسم عضو لن ينعكس على `MyVideos`
و`Admin` (تقرآن من `videos` مباشرة) بينما ينعكس على `Home`.

المقترح: الاعتماد على join فقط وإسقاط الأعمدة المكرّرة، أو العكس — المهم اختيار
واحد.

## 🟡 11. شرط ثلاثي بلا أثر

`src/App.jsx:942` — الفرعان متطابقان:

```js
go(s.user.must_change_password ? "mine" : "mine");
```

على الأرجح كان المقصود `"pwd"` في حالة الإجبار. السلوك الحالي سليم صدفةً لأن
مكوّن `App` يعترض الحالة عبر راية `mustChange`، لكن السطر مضلّل ويجب تبسيطه إلى
`go("mine")` أو تصحيح نيته.
